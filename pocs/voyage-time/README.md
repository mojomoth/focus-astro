# 우주선 항해 시간 계산 시뮬레이터 PoC

요구사항: `docs/prompts/POC_VOYAGE_TIME.md` (운영 규칙: `docs/prompts/POC_BASE.md`)
행성 데이터: `docs/design/refs/planet/README.md` → `planets.js`

## 실행

```bash
cd pocs/voyage-time && node scripts/serve.mjs   # 또는 npm run dev
# http://127.0.0.1:5180/
```

- 정적 파일만 필요하면 `python3 -m http.server 5180`으로도 열린다. 이때는 **밸런스 기록**이 비활성화된다.

- 설정을 바꾸면 주소창 쿼리에 기본값과 다른 값만 저장된다. `설정 링크 복사`로 그대로 공유할 수 있다.
- `JSON 복사`는 현재 밸런스의 구간별 수치(항해 시간, 실제 소요 시간, 순항 속도, 워프 상승, 도착일)를 내보낸다. 앱 구현에 바로 쓸 수 있다.
- 스크린샷과 콘솔 오류 확인(서버 실행 중일 때): `node scripts/shots.mjs verify http://127.0.0.1:5180/ <번호>`

## 밸런스 기록 (freeze)

밸런스를 결정하면 상단의 **밸런스 기록** 버튼을 누른다. 버전(v1, v1.1, v1.2.3)과 결정 이유를 적으면 `docs/design/freeze/balance/{version}/`에 스냅숏이 남는다.

| 파일 | 내용 |
| --- | --- |
| `docs/design/freeze/balance/{version}/README.md` | 요약 KPI, 밸런스 체크, 파라미터(기본값과 비교), 구간표, 메모, 재현 쿼리 |
| `docs/design/freeze/balance/{version}/balance.json` | 파라미터, 합계, 체크, 구간별 수치(항해·실제 소요·누적·도착일·순항 속도·워프 상승). 앱 구현용 |
| `docs/design/freeze/balance/README.md` | 전체 버전 목록. 기록할 때마다 다시 만든다 |

- 서버는 클라이언트가 보낸 파라미터만 받는다. 파라미터를 검증한 뒤 `freeze.js`로 다시 시뮬레이션해서 파일을 만든다.
- 같은 버전은 덮어쓰지 않는다(409). 수정이 필요하면 새 버전으로 기록한다.
- **기록된 밸런스** 카드에서 지난 버전을 **불러오기**할 수 있다. 현재 설정이 기록된 버전과 같으면 상단에 `vN 기록과 같음` 배지가 뜬다.
- 테스트할 때는 `FREEZE_DIR=/tmp/x node scripts/serve.mjs`로 기록 위치를 바꿀 수 있다.

### 밸런스 체크 기준

1. 첫 집중 30분 안에 첫 행성에 도착한다(첫 세션의 도착 경험).
2. 모든 구간이 한 번에 최대 사이클(기본 2사이클, 80분) 안에 끝난다. 실패하면 지구로 돌아가는 규칙 때문이다.
3. 하루 N사이클(기본 2사이클, 80분)로 목표 기간(기본 30일) 안에 완주한다. 구간은 날짜 사이에 쪼갤 수 없으므로, 하루 사용 시간보다 긴 구간이 하나라도 있으면 FAIL이다.
4. 우주선이 감속하지 않는다(속도 단조 증가).
5. 첫날 3곳 이상 도착한다(초반 이탈 방지).
6. 프록시마 b(첫 별)까지 누적 집중 시간이 3~8시간이다. 기획서 기준은 4시간 15분이다.

## 계산 규칙

- **항해 시간과 실제 소요 시간:** 집중 구간은 1배, 휴식 구간은 `restSpeed`배로 항해 시간이 쌓인다. 기획서의 "휴식 중 자동 항해"에 따라 기본값은 1배다. 1사이클(40분)에 항해 40분이 쌓인다.
- **구간:** 직전 목적지에서 다음 목적지까지를 구간 하나로 본다. 출항할 때마다 사이클 처음부터 시작한다. 실제 소요 시간과 집중 시간은 `sitting()`이 계산한다.
- **도착일:** 구간을 순서대로 날짜에 배치한다. 오늘 남은 시간에 다음 구간이 들어가지 않으면 다음 날 출항한다. 하루 사용 시간보다 긴 구간은 그만큼 날짜를 더 쓴 것으로 계산하고, 완주 체크에서 FAIL로 표시한다.
- **같은 항성계:** 프록시마 b·d, 트라피스트-1 e·f처럼 거리가 같은 행성은 `minLegMin`(기본 10분)의 궤도 이동으로 처리한다.
- **중간 기착지:** 기획서 마일스톤인 헬리오포즈(120 AU)와 오르트 구름 탈출(1.5광년)을 목적지로 넣는다. 해왕성에서 프록시마까지 거리가 약 9,000배 벌어지는 구간을 나누는 역할이다. 설정에서 끌 수 있다.

## 밸런스 모델

| 모델 | 정의 | 결과(기본 가정) |
| --- | --- | --- |
| **목표 구간 + 워프 래칫 (추천, 기본값)** | i번째 구간의 목표 시간은 `first·(last/first)^((i/(n-1))^shape)`다. 순항 속도는 `max(이전 속도, 구간 거리 ÷ 목표 시간)`으로 정한다. 속도는 필요할 때만 오르고 줄지 않는다 | 완주 집중 22시간 32분, 27일. 최장 구간 1시간 18분. 프록시마 b까지 누적 집중 4시간 44분(6일째). 속도는 0.077c에서 7,288만c까지 17단계로 오른다. 6/6 통과 |
| 연속 지수 가속 (물리형) | `T(d) = H·(ln(1+d/s) ÷ ln(1+d최대/s))^p`. p=1이면 속도가 거리에 비례한다(시간에 대해 지수 가속) | 행성이 거리 위에 뭉쳐 있어 구간이 고르지 않다. 오르트 구름 구간이 11시간을 넘는다. 2/6 통과 |
| 등속 1시간 = 1광년 (기획서 원안) | 등속 | 금성까지 1초가 안 걸리고(0.016초), 은하 중심부까지는 연속 1년 이상 걸린다. 3/6 통과 |

## 멀티에이전트 작업 기록

- **밸런스 설계·구현:** Claude Code(Opus 5.5). Python으로 모델 3개를 먼저 실험하고, 정적 페이지(`index.html`, `sim.js`, `app.js`)로 구현했다.
- **수치·코드 검증:** Codex CLI(`gpt-6.2-sol`, read-only). 결과는 `verify/codex-review.md`. 지적 사항을 반영했다.
  - 1초 미만 시간 표시가 60배로 나오던 버그와 `1시간 60분` 표시를 고쳤다.
  - 첫 구간 체크는 휴식 중 도착을 통과시키지 않도록 실제 소요 시간으로 판정한다.
  - 도착일은 하루 평균 환산을 버리고 구간 단위 날짜 배치로 바꿨다.
  - `sitting()`의 극소 입력 경계를 고쳤다.
  - URL 값은 컨트롤 범위로 자른다.
  - Codex 제안 1(하루 80분 기준)을 채택해 기본값을 바꿨다. 마지막 구간을 160분에서 80분으로, 한 번 최대를 4사이클에서 2사이클로, 곡선을 1에서 0.6으로 바꿨다. 리뷰 본문의 수치는 변경 전 기본값 기준이다.
- **외형 검증:** Claude CLI(`claude-sonnet-5-5`). `verify/*-2.jpeg`를 검증했다. 결과는 `verify/claude-review.md`. 보조 텍스트 대비 상향, 표의 목적지 열 고정, 모바일에서 부가 열 숨김을 반영했다. 결과는 `verify/*-3.jpeg` 이후 스크린샷이다. 리뷰는 축소 이미지를 본 것이라 일부 판독(예: '24시간 40분' 주석)은 실제와 다르다.
- 이 PoC는 이미지를 생성하지 않는다. 행성 썸네일은 `docs/design/refs/planet/images`를 112px로 줄여 썼다(`sips`).
